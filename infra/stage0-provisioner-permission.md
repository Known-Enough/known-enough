## Blocking limits: creation is not capped by IAM

The [CloudFront authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_cloudfront.html) and AWS's [machine-readable CloudFront reference](https://servicereference.us-east-1.amazonaws.com/v1/cloudfront/cloudfront.json) list no resource scope for distribution/OAC creation. They expose no condition for origin, distribution count, OAC name/type, configuration or spend. This candidate could create multiple or differently configured resources during its window. `us-east-1` selects the global service endpoint; it does not restrict edge delivery geography. Neither expiry nor a one-hour session stops charges from already-created resources. **The candidate cannot enforce the one-preview specification or the $25/month planning ceiling. Assignment and provisioning remain blocked pending an explicit decision on this residual authority and independent critical review.** No budget, credit, free-tier or hard cap is inferred.

Tagged distribution creation needs `cloudfront:TagResource`; a request-tag condition alone permits retagging unrelated resources if its ARN is a wildcard. This candidate instead proposes untagged creation, then exact-ARN tagging after an administrator removes the create/configuration statements and renders the newly observed ARN. It grants no CloudFront update/delete, invalidation or wildcard tagging. The operational exception to initial tagging must be accepted in review; no tag is an ownership/authentication proof. Required tag values and permitted keys are checked separately.

The remaining dangerous S3 `PutBucketPolicy` capability is deliberately absent. IAM cannot constrain its JSON body to the reviewed OAC-only grant. A later separately reviewed, single trusted CLI action must install [the OAC bucket policy](permissions/ke13c-preview-bucket-policy.json), using the observed distribution ARN and `--expected-bucket-owner 092954139775`. That action is outside this permission set and this preparation phase. If no authorized trusted identity exists, stop; do not add `PutBucketPolicy` or broaden this policy to work around the gate.

If the user requires an enforceable one-resource/spend boundary, do not assign the create candidate. Hand the exact reviewed resource requests to a trusted administrator for a single controlled provisioning session, or design/review an enforcement service under a new scope. An administrator still cannot turn an AWS Budget alert into a hard cap; a separately verified service plan/control would be needed for a hard financial guarantee. The existing $25 budget alert prerequisite remains.
