# B04 DynamoDB adapter and invitation implementation — local checks pass; independent review pending

Historical B04.5 verdicts remain scoped to their named commits. The current invitation issuance/redemption slice is locally implemented and awaits independent B04.5 review. This document records design and local verification only; no AWS resources have been created and no cloud behavior is claimed as verified.

## Identity boundary

- The production HTTP handler accepts only an `Authorization: Bearer` access token. `aws-jwt-verify` checks the configured Cognito user-pool issuer, signing key/signature, expiry, `token_use=access`, and one of two configured app client IDs. Missing, malformed, expired, wrong-pool, wrong-client, ID-token, and tampered tokens fail closed as 401 without logging token contents or verifier details.
- A participant app-client token maps only its verified Cognito `sub` to a participant principal. The application checks that subject against current room membership before reading owner state or returning a replay result. Client input never selects an owner or subject.
- A separate display app client maps to a read-only display principal only when the signed `cognito:groups` claim contains exactly one `deal-table-display-<roomId>` group. Group membership is an administrator-managed entitlement; the display client must not allow public sign-up or client-side group assignment. No display principal can read `/me` or write commands.
- Group removal cannot revoke an already issued self-contained access token. Before live use, configure a short access-token lifetime (proposed maximum 15 minutes), document that revocation delay, and verify it against the deployed user-pool configuration. G02 must review this bound. No user-pool configuration exists yet.
- The local `NON_PRODUCTION` header identity handler remains loopback-only and refuses to start when `NODE_ENV=production`. It is not used as a fallback by the Cognito handler.
- Room invitation issuance is restricted to the configured organizer and a pre-provisioned pending roster membership. The subject-to-member binding is fixed by trusted room provisioning; the issue request accepts only a member ID, never a subject or owner override. The invite token is returned once, stored only as a SHA-256 hash, and expires after 24 hours according to the application clock. Reissue is allowed only after expiry; an unexpired invite returns a conflict. Redemption requires the exact verified Cognito subject already bound to the pending member, activates only that member, and consumes the token in the guarded STATE transaction. Invalid, wrong-subject, expired and replayed tokens share the same not-found response. The token is not included in diagnostics or public snapshots. This flow cannot create or rebind memberships; production provisioning remains a trusted control-plane responsibility.

## Persistence and transaction design

Use one DynamoDB table. Each room has `PK=ROOM#<roomId>`; `SK=STATE` stores the bounded private room state and `SK=GUARD` stores the monotonically increasing repository commit version and replay counters. Replay receipts use `SK=REPLAY#<sha256(replay-key)>` and are separate items so command traffic cannot grow STATE. STATE schema version 4 stores room memberships as `PENDING` or `ACTIVE` and retains up to three invitation records alongside departed-owner exception grants and disclosure decision evidence in a private archive. Archived disclosure evidence keeps the preview hash and consent metadata but omits unshared preview wording; departed owners’ drafts and confirmations are not retained. No public browser imports or reads these rows.

- Read STATE and GUARD together with `TransactGetItems`. For a command, include only its matching REPLAY item in that transactional read; do not query or hydrate every room replay. Extend the repository transaction options with an optional replay-key hash and a safety-action candidate. For a request, derive a candidate only from the already verified principal plus raw string room/type/idempotency fields; the application later validates the envelope and recomputes the key after current membership authorization. The adapter may read that one matching receipt in the transaction but must not return it until the application callback has authorized against current room membership. A malformed or unauthorized request never learns whether a candidate row exists. It supplies the application transition a transient `RoomRecord` with zero or one matching receipt, rather than loading the whole replay history. For a changed transition, `TransactWriteItems` replaces STATE, conditionally increments GUARD at its observed version, and conditionally inserts that one REPLAY item. Creation conditionally inserts STATE and GUARD together. All room writers follow this guard discipline.
- Store only SHA-256 hashes of the canonical replay identity and canonical command body, plus the strict `CommandResult`; do not persist participant subjects or full private command bodies in replay records. The replay key digest binds principal kind, verified subject, room, command type and idempotency key. Authorization and current membership checks still happen before the receipt is returned. A body hash mismatch for the same key remains `IDEMPOTENCY_CONFLICT`.
- Replay receipts have no TTL and are never silently pruned. Per room, admit at most 4,096 ordinary new receipts, plus up to 192 permission-decision receipts and 320 safety-reserved receipts. The lifetime permission bound is 192 exception/disclosure history records across current and retired owners. A current owner can retain at most 32 of each type; when a roster revision removes an owner, archive that owner’s exception grants and disclosure decision metadata (including the preview hash but excluding unshared wording), and preserve the lifetime counter. Do not silently prune archived permission evidence; it stays private and is never projected into public or owner snapshots. Maintain separate GUARD counters for ordinary receipts, lifetime permission-history receipts, and safety-reserved receipts. Every new command receipt—including a permission decision or successful safety action—uses ordinary capacity first while the ordinary counter is below 4,096. A permission decision that appends history also increments the lifetime permission counter whether it used ordinary or reserved capacity; safety actions do not increment the safety-reserved counter while using ordinary capacity. Once ordinary capacity is exhausted, admit a new command receipt only for a valid pending permission decision with remaining lifetime permission allowance or a successful safety state change with remaining safety-reserved allowance. Increment the safety-reserved counter only for successful safety-action receipts committed after ordinary capacity is exhausted. Guarded repository transactions for snapshots, solver jobs, and expiry maintenance that create no command receipt may still update STATE; they do not increment replay counters and must preserve pending-response byte/receipt reservations. Thus 320 is an additional reserve after ordinary capacity, not a lifetime limit on safety actions. The maximum REPLAY rows are 4,608 per room. Existing authorized keys always replay before quota evaluation.

  **Safety-reserve bound:** after the ordinary quota is exhausted, no new `ACCEPT_PROPOSAL` command receipt can commit, so at most the three approvals already present can be withdrawn. The lifetime permission-history bound permits at most 192 exception/disclosure history records; each can create at most one revocable grant, so no more than 192 additional successful revoke receipts can be charged to the safety reserve. The worst case is 195 reserve-funded safety receipts, below the 320 cap. Declines and expiry transitions do not create extra revocable grants; expiry maintenance without a command receipt does not increment this counter.
- First authorize the current principal against STATE and validate the request before returning any quota result. Once ordinary capacity is reached, a deterministic admission rejection returns ROOM_CAPACITY_REACHED (HTTP 409) without committing a mutation, adding a REPLAY row, or incrementing a counter. The same unchanged key may be reevaluated after capacity changes; the client may issue a separate safety or consent command immediately. Do not spend permission or safety reserves on ordinary traffic. At ordinary capacity, a valid pending DECIDE_EXCEPTION or DECIDE_DISCLOSURE may consume one remaining permission slot only when the transition appends its bounded history record; a successful REVOKE_EXCEPTION, REVOKE_DISCLOSURE, or WITHDRAW_APPROVAL may consume a safety slot only when it commits that safe state change. An invalid, stale, or unsuccessful attempt consumes no reserved slot. If the matching reserve or encoded-size ceiling is exhausted, return known-no-commit ROOM_CAPACITY_REACHED (409) with no receipt/counter/state write. Application-level capacity results that are durably recorded under available quota remain ordinary semantic results with replay receipts. Keep 503 RETRYABLE_SERVER_ERROR for transient failures, exhausted transaction conflicts, storage outages, or uncertain commit outcomes; the client retains the exact envelope only for those uncertain outcomes. No request is reported as successfully applied without its receipt.
- Bound retained state histories before appending: at most 32 exception grants and 32 disclosure grants per owner, 64 immutable agreement receipts per room, and 32 published disclosure receipts per room. Reaching a history cap returns ROOM_CAPACITY_REACHED before the append; existing evidence is retained. Revocation, approval withdrawal, and application-clock expiry remain available at history capacity. When generating exception offers, reserve one exception-history slot per individual outstanding offer (including multiple overlapping offers for one owner), and reserve one disclosure-history slot for the owner's possible current-context preview. Do not issue any prompt unless every allowed response can be recorded. An exception decline fills its reserved exception slot and ends the round; a disclosure decline fills its reserved disclosure slot while preserving the already active exception. A disclosure preview and its later decision use the same reserved disclosure slot. These pending-response reservations are also bounded by the remaining permission-decision receipt allowance. Published words remain public once published, even if the grant is later revoked. Consent expiry continues to use application-clock checks; DynamoDB TTL is not used for authorization, expiry or revocation.
- Encode STATE as a strict envelope `{schemaVersion: 4, roomId, record}` with the `replays` property removed from `record`; the record includes a strict `retiredPermissionHistory` allowlist for exception/disclosure grants removed from the active roster. GUARD and REPLAY rows use their own explicit versions. Since no durable deployment exists, this is a local schema revision; any v3 or older durable data would require a separately reviewed explicit migration that preserves each grant and counter. Validate `roomId` against both the envelope and partition key. Decode STATE as a schema-versioned JSON payload. The production codec must conservatively measure the full DynamoDB STATE item, including keys, attribute names, encoded values, and item overhead, before every commit. Ordinary state transitions are limited to 352 KiB; permission responses (exception/disclosure ALLOW or DECLINE), grant revocation, approval withdrawal, expiry, and other safety transitions may use the protected hard ceiling of 360 KiB, below DynamoDB's 400 KB item maximum.

  For each pending exception offer, reserve its worst-case encoded STATE growth for both valid responses. At offer admission, if ALLOW can create the owner's current-context disclosure preview, reserve not only the exception-history replacement and preview creation, but also the preview's future response obligation: the worst-case additional encoded growth to replace that preview with a disclosure-history entry. Thus the admission reservation covers the full response path, including the new preview reservation; a later size check must not reject an already-issued ALLOW because its preview cannot be answered. Count exception-history response growth separately for every overlapping offer, but count the shared preview-and-response obligation once per owner and current context. Atomically transfer that shared reservation to the new pending preview when an eligible offer is allowed; release it only when no pending offer can still create the preview, or when context invalidation makes it impossible. For each already-pending disclosure preview, reserve the worst-case encoded growth of replacing it with its disclosure-history entry. Measure the maximum growth across each intermediate STATE on every allowed response path, including `status`, `controlVersion`, `job`, response wrappers, grant IDs/versions, and any other STATE fields changed by the real transition. Let `s` be the candidate STATE with the new offer persisted but not yet answered; `S(s)` is its encoded DynamoDB item size, `R_other(s)` is the byte obligation of other prompts at that point, `r_offer` is the incremental reservation for this offer (including the shared prospective preview chain only if it is not already held), and `R_after(t)` is every unrelated reservation remaining plus any new preview-response obligation introduced by path `t`. Require `r_offer >= max_t(S(t(s)) - S(s) + R_after(t) - R_other(s))`; `t` ranges over every prefix and full sequence of permitted responses, including exception ALLOW/DECLINE, any preview created by ALLOW, and that preview's eventual ALLOW/DECLINE. Check the size-plus-reservations invariant at every intermediate state as well. Compute with strict production STATE/GUARD codecs, maximum contract field and opaque-ID sizes, and full DynamoDB item-size accounting. Keep reservations recomputed from the guarded transaction state or versioned in GUARD, and include every counter/reservation change in its corresponding item-size check. Every writer must apply the same rule.

  Before persisting prompts, require `encodedCandidateStateBytes + pendingResponseByteReservations <= 360 KiB`; otherwise do not persist the prompt and return known-no-commit ROOM_CAPACITY_REACHED (409), with no receipt or counter write. For every ordinary write, require both `encodedCandidateStateBytes <= 352 KiB` and `encodedCandidateStateBytes + pendingResponseByteReservations <= 360 KiB`, so ordinary growth cannot consume headroom promised to pending responses. A protected permission, revocation, withdrawal, expiry, or safety write may exceed 352 KiB, but must still satisfy `encodedCandidateStateBytes + allStillPendingResponseReservations <= 360 KiB`. When a pending response commits, consume that prompt's reservation and require `encodedCandidateStateBytes + remainingPendingResponseReservations <= 360 KiB`. This preserves room for every outstanding response, including a decline, at the hard ceiling. Any deterministic capacity failure returns known-no-commit ROOM_CAPACITY_REACHED (409) without consuming the idempotency key, receipt, or counter; the unchanged key can be reevaluated after capacity changes. Replay items are limited to 8 KiB each; deterministic item-size rejection also returns 409 without a receipt. No oversized write is truncated or partially committed. Use retryable 503 only when the commit outcome is transient or uncertain.
- Decode private STATE with a strict allowlist schema: validate every nested contract/private field, reject extra or malformed fields, require the record's roomId to equal the ROOM#... partition key, and validate the exact STATE/GUARD sort keys. If both STATE and GUARD are absent, return null to the authorized application transition and do not surface a matching orphan REPLAY row; the existing application then returns the same non-enumerating 404 NOT_FOUND used for an existing room outside the caller's scope. A matching orphan replay receipt never authorizes access. Never reuse room IDs; if trusted creation cannot guarantee non-reuse, quarantine an absent pair with orphan rows rather than binding old replay data to a new room. Exactly one missing primary row, a mismatched key/room, malformed JSON, or an unsupported schema version fails closed as a redacted retryable server error. Room creation is allowed only when both primary items are absent and uses conditional puts. Do not auto-migrate unknown or older versions during requests; use an explicit reviewed migration that preserves every consent/agreement receipt.
- On cancellation, inspect the ordered DynamoDB `CancellationReasons`: retry conditional-check/transaction-conflict/throttle reasons with bounded backoff; map recognized deterministic item-size or item-collection capacity failures to known-no-commit ROOM_CAPACITY_REACHED; do not retry arbitrary validation failures. Keep exception details redacted. The solver runs outside the repository transaction; transition callbacks perform no external I/O. Retried callbacks may consume unused opaque IDs and bounded synchronous concession solving, but only committed results are returned. Exhaustion maps to the same retryable 503 path, never `422 INVALID_COMMAND` or a fabricated stale success. Expected-version mismatches remain semantic `STALE_CONTEXT` results; do not rewrite their versions.

## Runtime IAM boundary

The proposed adapter uses `TransactGetItems` for room reads, and `TransactWriteItems` with `Put` for STATE/replay/creation and `Update` for GUARD. The underlying item actions are therefore only `dynamodb:GetItem`, `dynamodb:PutItem` and `dynamodb:UpdateItem`; no `DeleteItem`, `ConditionCheckItem`, `Query`, `Scan` or table-management action is used by this design.

The following policy is a review example, not a deployed policy. Replace the placeholders with the one exact table ARN and confirm the final adapter action set before implementation:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RoomTransactionsOnly",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:UpdateItem"
      ],
      "Resource": "arn:aws:dynamodb:REGION:ACCOUNT_ID:table/DealTableRooms",
      "Condition": {
        "ForAnyValue:StringEquals": {
          "dynamodb:EnclosingOperation": [
            "TransactGetItems",
            "TransactWriteItems"
          ]
        },
        "ForAllValues:StringLike": {
          "dynamodb:LeadingKeys": [
            "ROOM#*"
          ]
        }
      }
    }
  ]
}
```

The transaction authorization follows AWS's underlying item-action rules and `dynamodb:EnclosingOperation` examples: [IAM for DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis-iam.html). `dynamodb:LeadingKeys` must use a `ForAllValues` modifier; `StringLike` supplies the `ROOM#*` prefix match: [DynamoDB condition keys](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/specifying-conditions.html).

Policy outcomes to verify against the final adapter (no IAM simulation has been run): the listed actions on the one table and `ROOM#*` keys are allowed only when enclosed by the two transaction APIs; direct `GetItem`/`PutItem`/`UpdateItem` calls are denied by the missing `EnclosingOperation`; any other table is denied by the exact Resource ARN; keys outside `ROOM#*` are denied by the leading-key condition. These are implicit denies because the policy grants no other access. The prefix is a storage namespace boundary, not a caller membership check; verified application authorization remains mandatory.

JWKS retrieval uses Cognito's public HTTPS JWKS endpoint and requires no Cognito API permissions. The display group is provisioned by a trusted administrator/control plane outside the request role. No IAM policy has been written or deployed.

## Current invitation issuance/redemption slice — 2026-09-24

The B04 invitation flow only operates on a membership provisioned as PENDING with an exact verified subject-to-roster-member binding. Only the configured organizer can issue an invitation. The request cannot provide a subject or owner override. The plaintext token is returned once, only its SHA-256 hash is persisted, and the 24-hour lifetime is checked by the application clock. An unexpired invitation cannot be reissued; after expiry, issue replaces the stored hash. Redemption authenticates the current Cognito subject, checks the stored binding and pending state, and activates that member and consumes the invitation in one STATE/GUARD transaction. Invalid, wrong-subject, expired and replayed tokens all return the same 404 shape. Closed rooms reject issue/redemption. The token is omitted from logs and all snapshot DTOs.

STATE schema v4 is local-only. Do not auto-decode or migrate v3 state; a durable v3 table needs a separately reviewed migration before this version can be deployed. Trusted room bootstrap must provision PENDING memberships; this slice does not add membership provisioning or invitation delivery. No Cognito user-pool configuration, live identity, IAM simulation, managed DynamoDB, deployment or cloud behavior has been verified.
