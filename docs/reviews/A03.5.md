## Open findings — owner A

### R1 — P1: final acceptance is enabled without the proposal terms

[OwnerScreen](../../apps/web/src/owner-screen.tsx), line 73; [acceptProposal](../../apps/web/src/command-client.ts), line 70.

In `/?view=owner&owner=approval`, “Confirm this exact approval” sends ACCEPT_PROPOSAL using `room.ownApproval`. The card shows an ID/version/hash from an existing receipt, but no full meeting, duty assignments or policy. There is no current ProposalView loaded or checked. The helper expressly accepts a FinalApproval as an alternative to proposal facts. A02 introduced this actionable path where A01 only displayed history. In the ordinary owner scenario, a first approval is unavailable entirely.

Browser reproduction: intercept the command route with a schema-valid success, open the approval scenario, inspect the final-acceptance card, then click the confirmation button. The probe confirmed an ACCEPT_PROPOSAL was sent despite the missing terms. Withdrawal emits its own WITHDRAW_APPROVAL command correctly.

Required correction: retain the receipt as history and bind new acceptance to an explicitly reviewed current public proposal with full terms and matching context/version/hash. Until that preparation is available, keep acceptance disabled; withdrawal may continue to use the existing receipt. Add coverage that receipt-only data cannot enable acceptance and that displayed terms match the submitted target. A hash by itself does not establish informed consent.

### R2 — P2: availability selection is ignored when building a draft

[OwnerScreen](../../apps/web/src/owner-screen.tsx), lines 55 and 70; [existing form test](../../tests/e2e/a01.spec.ts), line 44.

The radio changes `availability`, but `values()` only copies the existing conditions and changes the duty cost. Selecting “is available” therefore still submits the original NEGOTIABLE_UNAVAILABLE condition. The UI reports acceptance of a draft opposite to the displayed choice. The existing browser test selects this radio but asserts only the cost and command types, so it passes.

Browser reproduction: open `/?view=owner`, select “is available”, submit the draft and inspect the intercepted payload. The probe confirmed the radio stayed selected while the submitted condition stayed unavailable.

Required correction: map the selected full interval into the intended finite condition representation, preserving unrelated conditions and hard exclusions. Add assertions for both radio choices and the complete relevant conditions, not just the cost.

### R3 — P2: exception permission binds a policy the preview no longer displays

[OwnerScreen](../../apps/web/src/owner-screen.tsx), line 71.

A02 removed the policy label from the exception scope preview. The posted offer still binds `offer.scope.policy`, but the private screen displays only the roster, revision, interval, no-duty predicate and expiry. The agreed ranking policy is a material part of the exception scope and a policy change invalidates consent. The previous screen displayed it.

Browser reproduction: open `/?view=owner`, inspect the Exception region and click “Allow scoped exception” with intercepted HTTP. The command includes the balance-load policy; the region contains neither its label nor any policy text.

Required correction: restore the human-readable policy from the same scope used for the command. Assert that the preview and posted scope agree, including a changed-policy example, without replaying previous consent.

### R4 — P2: an unrecognized JSON response loses the original retry envelope

[browserCommandTransport](../../apps/web/src/command-client.ts), line 22; [sendCommand](../../apps/web/src/command-client.ts), line 84; [OwnerScreen.run](../../apps/web/src/owner-screen.tsx), line 41.

Fetch failures and JSON decoding failures become UnknownTransportError, but successful JSON decoding followed by CommandResult validation failure does not. A gateway can return JSON outside the result contract after a request was forwarded; the client cannot conclude whether the mutation applied. Instead it displays “could not be prepared or sent,” offers no unchanged retry, and generates a new idempotency key on the next click.

Browser reproduction: intercept the command response as HTTP 502 with `{"upstream":"unknown"}`. After one exception submission there is no “Retry unchanged request” control. Submitting again creates a different key. In contrast, a separate network-abort probe confirmed that the implemented explicit retry preserves the complete original serialized envelope byte-for-byte.

Required correction: preserve the original envelope whenever no trustworthy result can be established after dispatch, including invalid result shapes; offer the same explicit unchanged retry. Distinguish local pre-dispatch validation failures and valid server rejections. Add transport/browser tests for malformed JSON, valid JSON outside the schema and normal structured errors.

### R5 — P2: explicit input-confirmation preparation is absent

[OwnerScreen](../../apps/web/src/owner-screen.tsx), line 70; [command builders](../../apps/web/src/command-client.ts), line 58.

The frontend stops at SUBMIT_INPUT_DRAFT. Neither its source nor browser tests contain CONFIRM_INPUTS or reviewedIntervals, and there is no review/confirmation control in the draft scenario. This leaves the explicit owner-reviewed coverage requirement from [main integration](../main-integration.md#integration-changes-and-review) and [contracts](../contracts.md#logical-http-surface-and-command-preconditions) unimplemented. This is a missing preparation step, independent of whether B03 is running; no real server is needed to exercise it through injected responses.

Required correction: provide a separate draft review/confirmation action binding draft ID/revision and owner revision, with explicitly assessed full dated intervals. Never derive consent by automatically copying every schedule option. Cover confirmation against intercepted responses and require fresh review after a changed duration. Actual local negotiation remains A02.5 work.

## Boundaries that held and remaining limits

Public snapshots are independently parsed through strict allowlisted schemas, never constructed from private object spreads. The frontend imports contracts and UI dependencies, with no server/test-support fixture imports. Across collecting, blocked, private-review, proposed, agreed and superseded browser scenarios, no owner chunk was requested and no owner value markers or receipt text appeared in the DOM/console. Production asset inspection confirmed owner mock values remain in the lazy owner chunk. That downloadable chunk contains deliberately synthetic examples; lazy loading is not access control. The existing bundle scan detects seeded server markers only and is not a general privacy proof.

Exception and disclosure commands are separate and carry no client owner-identity field. The disclosure preview preserves wording, audience and inference warning. Rendered errors use safe codes/generic text; source inspection found no frontend console logging, analytics or local/session storage of owner payloads. The public UI has no mutation controls. Existing stale-response tests confirm no automatic replay, and stale read controls remain disabled until refresh. Mobile overflow, keyboard navigation and reduced-motion checks pass.

Missing evidence: current snapshots still come from fixed owner mocks and a hardcoded synthetic decision revision; a stale refresh does not demonstrate receipt of a newer real context. Successful commands do not establish updated server projections. A03 exercises active and empty receipts, but provides no transition coverage for declined/revoked/expired/superseded history or actual publication. No authenticated isolation, real API negotiation, transaction/expiry enforcement or live acceptance is established. Those later gates remain distinct from these frontend findings.
