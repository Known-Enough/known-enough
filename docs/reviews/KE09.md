## Findings

### R1 — High: a generated owner question can disclose another owner's private rule

**Probe P1 reproduced.** In the ready Christmas fixture, the injected negotiation model copies Maya's confirmed HARD budget rule into the adjustment for Nina's destination question. `generate(maya)` returns `NEEDS_PERMISSION`; Nina's owner snapshot contains that entire rule, including `maya-budget-rule` and the private USD 160,000 minor-unit limit. No disclosure was requested or approved. The existing browser renderer would format the amount in the question; the probe verified the owner DTO, not a browser screenshot.

[Decision negotiator](../../packages/application/src/decision-negotiator.ts), `parseQuestionIntents` (line 48), validates the target owner/constraint but accepts an arbitrary typed adjustment. [Application](../../packages/application/src/known-enough.ts), `ownerRulesValid` (line 72) and `validatePendingNegotiationAdjustment` (line 567), check visible variable references and whether the adjustment admits the candidate. A private bound on a public variable passes both checks. [Question rendering](../../apps/web/src/known-enough-home.tsx), line 317, renders the accepted typed rule. Removing free text does not establish the provenance of typed literals or IDs.

**Required correction:** constrain adjustments to the target owner's negotiable condition and explicitly permitted public/owner-derived values; generate safe identifiers at the boundary. Reject copied cross-owner rules, bounds and encoded identifiers before storing or delivering a question. Define and enforce the architecture's publication policy for values derived from private inputs in public candidates too. Add a poisoned-model regression with distinct synthetic private canaries; merely checking that an output references public variables is insufficient. This is a model-output poisoning test and does not claim any particular live provider would generate the payload.

### R2 — Medium: a successful constraint revision makes the owner unreadable

**Probe P2 reproduced.** Confirm Maya's existing draft again with the same constraint IDs and current versions. The confirmation command succeeds. The next `getOwnerSnapshot(maya)` throws `ZodError: Owner constraint IDs must be unique`.

[Application](../../packages/application/src/known-enough.ts), `CONFIRM_CONSTRAINTS` (line 969), retains the superseded record and appends a new version with the same ID. [Owner snapshot contract](../../packages/contracts/src/known-enough.ts), line 901, requires unique IDs across the whole returned history. Subsequent owner draft/command preparation cannot load the owner view.

**Required correction:** reconcile history identity and the current-owner projection, retaining historical evidence without violating current snapshot invariants. Cover repeated same-ID edits and pending/answered questions that reference an older constraint version. A successful transition must leave both storage and every authorized read schema valid.

### R3 — Medium: retiring a disclosed proposal breaks reads for its audience

**Probe P3 reproduced.** Generate a valid Cancun proposal; Maya explicitly allows an exact synthetic note to Leo only; publish it. Leo sees the note and Nina does not. Close the decision using the creator's current control version. Leo's next public read throws `Disclosure must bind to the current exact proposal and context`; Nina can still read `CLOSED`.

[Application](../../packages/application/src/known-enough.ts), `closeDecision` (line 766) clears the proposal but leaves `publishedDisclosures`; `publicSnapshot` (line 198) filters only by audience. [Public snapshot contract](../../packages/contracts/src/known-enough.ts), line 791, requires each projected disclosure to match a current proposal/context. The same retained-history mismatch is present by inspection in revision/proposal retirement; only close was executed in P3.

**Required correction:** preserve authorized historical receipts separately from the current-proposal projection, or explicitly model their historical lifecycle. Cover close, frame/roster revision, constraint change, dependency expiry/revocation and replacement. Keep exact audiences intact. Also reconcile unscoped projection's `requiredParticipantIds` filter with the schema's all-current-participants audience rule; optional roster members must not cause invalid unscoped reads. That optional-member edge was inspected, not separately executed.

### R4 — High: equivalent typed requests bypass an owner's refusal

**Probe P4 reproduced.** Nina declines `destination EQ mazatlan`. On a second reasoning call the model requests `destination IN [mazatlan]`. The application creates a second PENDING question with a different identity for the same concession.

[Request identity](../../packages/contracts/src/known-enough.ts), `serializeNegotiationRequestIdentity` (line 1133), removes labels and normalizes sets but preserves the operator representation. [Application](../../packages/application/src/known-enough.ts), `askNegotiation` (line 383), suppresses only matching hashes. The existing refusal test repeats the identical representation and does not cover this equivalent form.

**Required correction:** give the supported concession vocabulary a canonical semantic identity, including singleton membership/equality and other equivalent supported encodings, or restrict question generation to one canonical representation. Verify equivalent requests remain suppressed after refusal while a genuinely different scoped adjustment is handled under the agreed no-pressure policy. This finding touches KE01 authored in this conversation; independent follow-up remains necessary.

### R5 — High: material private-condition changes preserve old consent

**Probe P5 reproduced.** Nina allows the destination exception. Maya then confirms a changed HARD budget, from 160,000 to 170,000 USD minor units, with a new constraint ID to avoid R2. The context token stays unchanged, Nina's old grant stays ACTIVE, and the next proposal applies using that old grant without new frame confirmation or renewed permission.

[Application](../../packages/application/src/known-enough.ts), `CONFIRM_CONSTRAINTS` (line 969), retires the proposal and changes the submitting owner's records, but does not rotate semantic/context authority or supersede other current grants/confirmations. The [architecture state rules](../known-enough-architecture.md#lifecycle-and-proposal-identity) require material confirmed-condition changes to supersede dependent authority and return to frame confirmation.

**Required correction:** distinguish initial input collection from material revisions and implement the specified conservative invalidation in one transaction. Recheck jobs, all affected grants/questions, frame confirmations and approvals. Add a sequence proving an old permission cannot authorize a proposal after a material confirmed-condition change. The probe did not need or claim an unauthorized final approval.

### R6 — Medium: valid overlapping rule IDs crash completion and strand reasoning

**Probe P6 reproduced.** Give Maya's private HARD rule the same rule ID as a public definition rule; both are otherwise valid and their scoped inputs are accepted. Generate the valid Cancun candidate. Completion throws a Zod error at `validation.checkedRuleIds`; the persisted decision remains `REASONING`.

[Kernel](../../packages/domain/src/known-enough-kernel.ts), `recordRule` (line 573), accumulates bare IDs across public and private rule scopes. [Application](../../packages/application/src/known-enough.ts), line 693, reparses that list into [CandidateValidation](../../packages/contracts/src/known-enough.ts), line 524, which requires unique IDs and allows only 128. The generic input permits 128 definition rules plus 64 active private constraints, so the aggregate maximum also needs reconciliation (that larger-bound case was identified by inspection, not executed). [Negotiator](../../packages/application/src/decision-negotiator.ts), line 210, does not release the job on a completion exception.

**Required correction:** use an unambiguous scoped validation receipt with compatible aggregate bounds, or normalize internal accounting into a valid bounded receipt without losing diagnostics. Clean up the exact job after failed completion without cancelling newer work. Add collision, aggregate-bound and recovery regressions. Contract/kernel corrections require independent follow-up because of prior authorship here.
