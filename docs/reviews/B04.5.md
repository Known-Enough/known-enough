## Findings

### R1 — P1: authenticated debug mode logs identity and private owner metadata

Affected: [authenticated handler options and composition](../../apps/api/src/index.ts), especially `ApiHandlerOptions.debug` (line 41), `actor` (107–108), `logOwnerSnapshot` (119–125), and `createApiHandler` (304–312).

The new authenticated handler forwards `debug: true` into diagnostics originally intended for synthetic local identities. A successful authenticated `/rooms/:roomId/me` request writes the verified subject, room, input/draft presence, reviewed-interval count, exception-offer count, disclosure-preview count and approval state to `console.log`. Successful public reads and command paths also log the subject. This associates a real identity with owner-only state once real credentials are used, contrary to the repository's privacy/logging boundary. The option defaults to false, which limits exposure, but there is no restriction or redaction when it is enabled on the exported authenticated composition.

Independent reproduction: create a real application/in-memory room with a synthetic canary subject, serve `createApiHandler({ application, identityResolver, debug: true })`, and fetch that subject's `/me`. Status is 200; captured console output contains the subject and `exceptionOffers=` / `disclosurePreviews=`. The probe asserted this and exited 0; it did not print the captured lines or use real participant data. Existing log coverage only checks that an invalid command type is not logged.

Required correction by A/Ricardo: disable the local diagnostics for the authenticated handler or introduce an explicit safe diagnostic projection that excludes identity and private owner/consent state. Add a regression covering authenticated reads, commands and errors with diagnostic mode requested; retain permitted local synthetic diagnostics only where deliberately bounded. Follow-up must inspect the final fields, not merely assert absence of raw tokens.

### R2 — P2: committed identity tests bypass the actual security configuration

Affected: [resolver tests](../../apps/api/src/cognito-identity.test.ts) and [authenticated HTTP tests](../../tests/integration/http.test.ts); production configuration is in [the resolver](../../apps/api/src/cognito-identity.ts), lines 38–42 and 73–82.

All four committed resolver tests inject a fake `verify`, and both new HTTP tests inject a principal-returning resolver. They do not execute `CognitoJwtVerifier.create` or the environment factory. Consequently changing/removing the required client, pool or access-token constraint would leave these regressions green. The current configuration is correct by inspection and the independent offline probe below; this finding concerns missing durable coverage of the task's central security boundary, not an observed signature bypass.

Required correction by A/Ricardo: add offline signed-token/JWKS tests exercising the real configured verifier and environment factory, including wrong issuer/pool, wrong client, ID-token rejection, expired token, invalid signature and missing/invalid configuration. Use generated synthetic keys and a local key cache or injected key-fetch seam; no live Cognito is required. Keep claim mapping tests, and test that resolver failures produce a generic 401 without logging verifier/token details. Avoid replacing these assertions with a fake verifier that simply returns the expected claims.

## Reviewed behavior

- `aws-jwt-verify` is pinned to 5.2.1 in the API manifest and lockfile. The default factory supplies `userPoolId`, `clientId`, and `tokenUse: 'access'`; it does not accept issuer or role from request input. Installed dependency code verifies the signature and configured issuer/client/token use and enforces expiry/nbf when present. No AWS credentials are needed by this local verification code. Missing environment values fail startup, rather than falling back to test identities.
- Principal mapping reads only verified `sub` and group claims. The existing bounded `Id` schema accepts normal Cognito subjects. Invalid subjects, non-array/non-string group values, an empty display suffix and multiple display-prefixed groups fail closed. A single exact `deal-table:display:<room-id>` group yields only a display principal. Other groups confer no organizer/service authority. No display group yields a participant candidate whose room membership remains server-controlled. Group administration and token lifetime are separate deployment obligations below.
- Identity resolves before route/body handling (except harmless CORS preflight). HTTP route authorization calls the application before JSON parsing and replay lookup; display writes are denied before parsing. The application then rechecks operation authorization inside the transaction before strict command validation or returning a cached result. Membership removal therefore prevents replay. Organizer privileges come from the stored organizer subject, owner identity from stored subject-to-member mapping, and service operations are excluded from the HTTP principal type/mapping.
- Display credentials read only their bound room's allowlisted public projection, receive 403 for `/me` and commands, and 404 for other/absent rooms. Owner snapshots remain separately constructed. This retains the existing disclosure-audience filtering and introduces no public private-object spread or browser import of backend code.
- Resolver/token/key-fetch exceptions become null identity/401 with stable code-only responses and no verifier diagnostics. Repository/application unexpected errors retain the existing generic `INVALID_COMMAND` behavior. JWKS outages currently look like invalid credentials to clients; safe operational metrics and retry behavior remain production-composition work. No raw token logging was found. R1 concerns a different diagnostic path after successful identity resolution.
- Local synthetic identity allowlisting, loopback startup and production guard remain intact. The generic handler ignores the test-identity header; wire command/snapshot schemas are unchanged. Existing HTTP tests exercise errors, replay authorization, privacy and the complete synthetic negotiation through the shared handler.

## Remaining B04/G02 review delta

These are unimplemented/incomplete production gates, not evidence that the small identity slice already implements or fails them:

1. Define and review who may create/assign/remove display groups, configure token-generation triggers, manage subject-to-room memberships and bind single-use invitations. Untrusted users must not mint scopes or bind themselves to another owner. A group name is an application permission here; it is not an IAM policy. Cognito groups appear in signed tokens and group administration uses AWS-authorized operations. [AWS group documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-user-groups.html).
2. Specify dedicated display-account lifecycle, token storage/refresh/expiry and revocation behavior. Display reads currently trust the still-valid signed group without a server-side display-session record. Removing membership from Cognito does not rewrite an issued JWT. Revocation/sign-out is not established by signature verification; AWS explicitly documents that revoked tokens can still pass generic signature/expiry validation. Decide whether bounded token lifetime is acceptable or add application revocation checks, then test the chosen policy before G02. [AWS revocation documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/token-revocation.html).
3. Review actual user-pool/client settings, issuer behavior, key rotation/outage handling, API Gateway/Lambda composition, trusted service/job identity and least-privilege IAM when those artifacts exist. The current shared Node handler still runs local queued work using a constructed service principal; it is not an SQS/production worker design. Real access tokens carry subject, client and group claims, but accepting those locally does not establish the deployed configuration. [AWS access-token documentation](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-access-token.html).
4. Implement and review the DynamoDB repository's conditional/transaction behavior, application-enforced expiry, agreement/revocation races, duplicate commands/consumers and durable membership/invite replay. `infra` remains a placeholder and the only repository is in-memory; no IAM policy or DynamoDB implementation is approved by this review.
5. Review the corrected R1/R2 artifact independently, then the subsequent critical identity/persistence changes and actual browser/session evidence at A04.5/G02. Production CORS, abuse bounds, safe operational diagnostics and reconnect/session behavior remain unverified. G02 and human acceptance remain required before external testers.
