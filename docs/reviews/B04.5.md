### R1 — P2: proposed IAM actions do not authorize DynamoDB transactions

Location: [infra/README.md:26](../../infra/README.md). The proposal grants only `dynamodb:TransactGetItems` and `dynamodb:TransactWriteItems`. DynamoDB transaction authorization uses the underlying item actions, so this policy does not establish the permissions needed for the proposed reads and writes. AWS documents `GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`, and `ConditionCheckItem` as applicable actions, with `dynamodb:EnclosingOperation` for restricting them to transactions. [AWS transaction IAM documentation](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis-iam.html).

Correction owner A: replace the proposed action list with the minimum underlying actions actually used by STATE/GUARD operations, one exact table ARN, and an enclosing-operation restriction. Define the `LeadingKeys` condition using the required `ForAllValues` modifier and appropriate pattern operator for `ROOM#*`; this prefix limits the storage namespace, not individual caller room membership. Include allow/deny policy cases for both transactional operations, direct item access, other tables and keys outside the prefix. [AWS condition-key documentation](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/specifying-conditions.html). No deployed policy or IAM simulation was available; this is a verified documentation/design error.

### R2 — P2: the storage proposal has no safe size/history or decoding strategy

Location: [infra/README.md:15](../../infra/README.md), [infra/README.md:22](../../infra/README.md), and [RoomRecord](../../packages/application/src/types.ts). The two-item design stores the entire room in STATE while `execute` appends a replay body/result for every new authorized valid command key, including application rejections. Agreement and permission histories also grow. The proposal acknowledges the 400 KB item limit but supplies no bounded representation or lifecycle. Repeated valid requests can therefore grow STATE until later writes, including permission revocation, fail. Rejecting an oversized write alone does not preserve a usable consent lifecycle. A schema-version field is proposed without defining runtime decoding, migration or rejection of corrupt/unknown versions.

Correction owner A: choose and document a concrete storage/history/replay strategy before implementation. Define byte/count limits, idempotency retention semantics, preservation of agreement/consent evidence, and how withdrawal/revocation/expiry remain possible at capacity. Define a validating private-record codec, key/room binding, missing or mismatched STATE/GUARD handling, and unknown schema-version behavior. This may require a bounded room lifecycle or separating retained records; do not silently prune evidence or change replay guarantees. Required adapter tests must cover near-limit operations, safe revocation, duplicate replay and malformed persisted rows. This is an unresolved design gate, not a reproduced DynamoDB failure. [AWS transaction limits](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).

### R3 — P2: exhausted storage retries would become a non-retryable client error

Correction owner A: specify and implement a redacted server/transport error path for contention exhaustion, storage outages and unknown commit outcomes; coordinate shared contracts if adding a result code. Preserve the original command envelope/key for uncertain outcomes. Classify retryable transaction conflicts separately from validation/size failures; an application stale-context result must remain a semantic rejection, without rewriting expected versions. ## Inspected boundaries and design constraints

- `createCognitoIdentityResolver` uses the configured pool, access-token use, both explicit client IDs and zero expiry grace; it maps only verified `sub`. Display mapping requires the display client plus exactly one valid prefixed room group. Participant tokens do not become display credentials merely because of groups. - The production handler has no mock-header fallback. Except for preflight, authentication precedes URL routing and body parsing; room authorization precedes command parsing and the application authorizes again before replay lookup. CORS reflects only exact configured origins; it is not the authorization mechanism. `no-store` remains on JSON responses. Diagnostic changes remove stable subject/roster identifiers and retain bounded actor kinds, validated command types and counts; no token or private values were added.
- Admin-only group management and separate client configuration are deployment assumptions, not proven by a signed group claim. The documented proposed 15-minute token lifetime/revocation delay still needs an actual configured bound and G02 acceptance. Dedicated display credential provisioning, client sign-up/auth flows, group administration and lack of participant memberships must be verified before live use; no user-pool infrastructure exists here.
- Transactional STATE/GUARD reads and a conditional GUARD update alongside STATE replacement are a reasonable optimistic concurrency outline. All writers must obey it; discarded callback attempts must never leak results or partial mutations. Callbacks inspect current membership and expected versions again on retry. Reads can mutate state through expiry sweeps/readiness changes and must participate in the same commit discipline.

### R2a — P2: known capacity rejection would lock the client out of safety actions

Locations: [infra/README.md:19,21](../../infra/README.md), [command-client.ts:104–113](../../apps/web/src/command-client.ts), [owner-screen.tsx:110,126–127](../../apps/web/src/owner-screen.tsx).

The proposal returns retryable 503 for a new ordinary request after all 4,096 ordinary receipts have been used, and for a normal write exceeding 352 KiB. It explicitly knows these requests did not commit. The client correctly treats this 503 as an uncertain outcome, retains its exact command and disables other commands (including withdrawal) while awaiting resolution. An exact retry at permanent ordinary capacity returns the same 503 forever. At byte capacity, the proposal expects a revocation/expiry to free room, yet the affected browser's other commands are disabled. The backend's reserved safety allowance therefore does not make those actions usable in this client flow. This is a design/source incompatibility; no DynamoDB adapter exists to reproduce it end to end.

Correction owner A: return an explicit known-no-commit capacity rejection, such as the existing `ROOM_CAPACITY_REACHED`, for deterministic admission/size rejection after authorization; retain 503 only for transient/uncertain storage outcomes. Add a client regression that receives the capacity response and can then submit a withdrawal/safety action; retain the unknown-outcome retry regression. ### R2b — P2: both absent storage rows must preserve the normal missing-room result

Location: [infra/README.md:22](../../infra/README.md). The new codec design classifies both STATE and GUARD missing as a retryable server failure, alongside one missing row or malformed data. Both absent is the normal nonexistent-room state. Existing application authorization returns `404 NOT_FOUND` for a missing room and for an existing room outside the caller's membership/scope. Implementing the proposal literally would instead return 503 for nonexistent rooms and 404 for existing unauthorized rooms, making existence distinguishable and converting normal absence into an outage.

Correction owner A: return null to the authorized application transition when both rows are absent so the existing non-enumerating NOT_FOUND behavior applies. Keep one missing row, inconsistent keys/schema or corrupt state as fail-closed storage errors. An orphan replay receipt must not become an authorized replay when STATE/GUARD are absent. Add adapter/HTTP cases comparing nonexistent and unauthorized-existing room responses once the adapter is built. This is a design finding, not a claim that the unimplemented codec currently leaks data.

### R5 — P2: history limits can prevent an owner from declining an open offer

Locations: [application index.ts:369–395](../../packages/application/src/index.ts) and [offerConcessions:552–577](../../packages/application/src/index.ts). Once an owner has 32 retained exception receipts, an offered exception cannot be declined: the transition throws `ROOM_CAPACITY_REACHED`, the working-state rollback restores the offer, and the room stays in PRIVATE_REVIEW. The current new regression tests only ALLOW rejection and revocation of an existing grant, so they miss this behavior. The same unconditional cap guards disclosure decline; the proposed post-4,096 reserve also excludes both decline commands.

Independent probe: use the real application/in-memory repository and fixture to reach a pending Nina offer, seed 32 synthetically retained DECLINED exception receipts (using the same bounded-history setup technique as the committed regression), then send the matching DECLINE command. Observed `ROOM_CAPACITY_REACHED`, one pending offer, and PRIVATE_REVIEW. The inline probe exited 0 after asserting that defect. This is a locally reproduced application defect; no real participant data or DynamoDB was used.

Correction owner A: make pending refusal possible at capacity. Reserve enough history/replay space when issuing offers/previews, or use another bounded design that can record a decline without deleting evidence or stranding a prompt. Account for every pending response, including multiple overlapping exception offers for one owner and independent disclosure refusal, and revise safety-reserve accounting if needed. Do not create a prompt whose decline cannot be committed. Add full/near-capacity offer-generation and DECLINE regressions, including confirmation that exception refusal ends the round and disclosure refusal preserves an otherwise valid exception.

### Persistence design assessment

Separate REPLAY rows and canonical SHA-256 key/body digests address STATE growth from full private command bodies. The proposed transient zero/one replay model is implementable with an explicit transaction option and recomputed authorized key; those repository options and the DynamoDB adapter are still future work. Retry attempts must reconstruct a fresh working record, authorize current membership, discard unsuccessful mutations/results and condition every write on GUARD. Callback reads can sweep expiry and need the same commit discipline. Main asynchronous solving remains outside transactions; bounded synchronous concession search still runs inside a callback, as now acknowledged.

The proposed 320 successful safety receipts exceed the stated conservative count of 192 permission grants plus 64 agreement withdrawals plus at most two approvals on a partial proposal (258). Normal commands cease after the ordinary allowance, so they cannot replenish those safety targets. This calculation does not cover the outstanding decline problem in R5. The 352/360 KiB STATE ceilings and 8 KiB REPLAY ceiling are below service item limits; revocations/expiry mainly change bounded statuses/counters or remove current state, but the future codec must measure actual encoded bytes and test the 8 KiB safety headroom across all allowed transitions. Immutable histories can reach byte capacity before count caps, so deterministic capacity handling must be coherent independently of those counts.

Strict nested allowlists, exact row keys/room IDs, explicit schema versions and reviewed migration are specified, with the absent-pair correction in R2b required. No codec, byte-budget enforcement, ordinary/safety counter enforcement, or transaction-race implementation exists yet. Those remain implementation/G02 evidence requirements; this review does not mistake the proposal for working persistence.
