## Findings

### R1 — P2: proposed IAM actions do not authorize DynamoDB transactions

Location: [infra/README.md:26](../../infra/README.md). The proposal grants only `dynamodb:TransactGetItems` and `dynamodb:TransactWriteItems`. DynamoDB transaction authorization uses the underlying item actions, so this policy does not establish the permissions needed for the proposed reads and writes. AWS documents `GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`, and `ConditionCheckItem` as applicable actions, with `dynamodb:EnclosingOperation` for restricting them to transactions. [AWS transaction IAM documentation](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis-iam.html).

Correction owner A: replace the proposed action list with the minimum underlying actions actually used by STATE/GUARD operations, one exact table ARN, and an enclosing-operation restriction. Define the `LeadingKeys` condition using the required `ForAllValues` modifier and appropriate pattern operator for `ROOM#*`; this prefix limits the storage namespace, not individual caller room membership. Include allow/deny policy cases for both transactional operations, direct item access, other tables and keys outside the prefix. [AWS condition-key documentation](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/specifying-conditions.html). No deployed policy or IAM simulation was available; this is a verified documentation/design error.

### R2 — P2: the storage proposal has no safe size/history or decoding strategy

Location: [infra/README.md:15](../../infra/README.md), [infra/README.md:22](../../infra/README.md), and [RoomRecord](../../packages/application/src/types.ts). The two-item design stores the entire room in STATE while `execute` appends a replay body/result for every new authorized valid command key, including application rejections. Agreement and permission histories also grow. The proposal acknowledges the 400 KB item limit but supplies no bounded representation or lifecycle. Repeated valid requests can therefore grow STATE until later writes, including permission revocation, fail. Rejecting an oversized write alone does not preserve a usable consent lifecycle. A schema-version field is proposed without defining runtime decoding, migration or rejection of corrupt/unknown versions.

Correction owner A: choose and document a concrete storage/history/replay strategy before implementation. Define byte/count limits, idempotency retention semantics, preservation of agreement/consent evidence, and how withdrawal/revocation/expiry remain possible at capacity. Define a validating private-record codec, key/room binding, missing or mismatched STATE/GUARD handling, and unknown schema-version behavior. This may require a bounded room lifecycle or separating retained records; do not silently prune evidence or change replay guarantees. Required adapter tests must cover near-limit operations, safe revocation, duplicate replay and malformed persisted rows. This is an unresolved design gate, not a reproduced DynamoDB failure. [AWS transaction limits](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).

### R3 — P2: exhausted storage retries would become a non-retryable client error

Location: [infra/README.md:19](../../infra/README.md), [applicationError](../../apps/api/src/index.ts), and [HTTP catch](../../apps/api/src/index.ts). The proposal promises a retryable server error after bounded transaction retries, but the shared production/local handler maps every non-ApplicationError to `422 INVALID_COMMAND`. The client treats this valid rejection as a resolved outcome and loses the unchanged-request retry path. This is especially misleading if a queued mutation committed before subsequent worker/storage work failed.

Independent synthetic loopback probe supplied a `getPublicSnapshot` that throws `Error('synthetic storage retry exhausted')` to the shared handler through `createLocalApiHandler`; it returned exactly `422 INVALID_COMMAND`. This confirms the mapping, not a real DynamoDB outage.

Correction owner A: specify and implement a redacted server/transport error path for contention exhaustion, storage outages and unknown commit outcomes; coordinate shared contracts if adding a result code. Preserve the original command envelope/key for uncertain outcomes. Classify retryable transaction conflicts separately from validation/size failures; an application stale-context result must remain a semantic rejection, without rewriting expected versions. Add a handler regression and a committed-but-response-lost/retry regression with the real adapter once available.

The production HTTP test covers missing bearer authentication and CORS, but no valid signed participant/display request. These tests can pass if the production verifier's issuer/client/token-use configuration or its call wiring regresses.

Correction owner A: feed local signed tokens and controlled JWKS through the actual resolver and `createCognitoApiHandler`, preserving real library signature verification. Cover valid participant owner access, subject/owner substitution, display public-only and cross-room scope, membership removal before cached replay, and wrong issuer/client/use/expiry/signature. Verify unauthenticated or unauthorized malformed bodies never reach detailed parsing, and auth failures emit no token/claim diagnostics. A controlled JWKS transport/cache seam is preferable to replacing verification with an always-successful identity stub. Local tests remain distinct from Cognito service acceptance.

## Inspected boundaries and design constraints

- `createCognitoIdentityResolver` uses the configured pool, access-token use, both explicit client IDs and zero expiry grace; it maps only verified `sub`. Display mapping requires the display client plus exactly one valid prefixed room group. Participant tokens do not become display credentials merely because of groups. Errors expose no verifier details.
- The production handler has no mock-header fallback. Except for preflight, authentication precedes URL routing and body parsing; room authorization precedes command parsing and the application authorizes again before replay lookup. CORS reflects only exact configured origins; it is not the authorization mechanism. `no-store` remains on JSON responses. Diagnostic changes remove stable subject/roster identifiers and retain bounded actor kinds, validated command types and counts; no token or private values were added.
- Admin-only group management and separate client configuration are deployment assumptions, not proven by a signed group claim. The documented proposed 15-minute token lifetime/revocation delay still needs an actual configured bound and G02 acceptance. Dedicated display credential provisioning, client sign-up/auth flows, group administration and lack of participant memberships must be verified before live use; no user-pool infrastructure exists here.
- Transactional STATE/GUARD reads and a conditional GUARD update alongside STATE replacement are a reasonable optimistic concurrency outline. All writers must obey it; discarded callback attempts must never leak results or partial mutations. Callbacks inspect current membership and expected versions again on retry. Reads can mutate state through expiry sweeps/readiness changes and must participate in the same commit discipline.
- The injected main solver runs outside the repository transaction, but the claim that all solver work is outside it is too broad: `offerConcessions` performs bounded synchronous `solveDecision` calls inside the result-application callback. No external I/O was found there; repeated callback execution may consume IDs and repeat bounded computation. Record this accurately and keep callback side effects constrained.
- Before G02, inspect the final adapter, actual IAM policy, membership/invite redemption and replay, codec, oversize behavior, authorization before cache, concurrent approval/revocation, stale revisions/jobs, commit ambiguity, and expiry under real adapter races. This first slice implements none of those live storage/invite checks.
