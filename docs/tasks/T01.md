## Acceptance

1. Define a bounded TeamTable example: “Prepare our launch rehearsal and divide the weekend responsibilities.” AI clarifies meeting options, roles and the ranking principle; participants confirm supported structured terms before they become authoritative. Unsupported goals receive clarification or a clear limitation. General travel/budget/project scheduling is future template work, not an MVP promise.
2. Specify three presentation moments: privately interpret a participant's preference and request confirmation; explain a current solver-supported conditional exchange only to its owner; answer shared questions about the current proposal, agreement status and authorized published statements. Include example inputs, exact available data, output forms, failure states and UI locations.
3. Define separate model contexts and server-enforced tool permissions. Private extraction sees one verified owner's information. The deterministic solver checks confirmed conditions across participants. The shared assistant receives strict public allowlisted facts and currently authorized published disclosures only; never raw private input, rejected disclosures, refusal details, private grant IDs, private scores or owner-attributed conflicts. No shared conversation memory may inherit private context.
4. AI may suggest and explain; it cannot invent feasibility, silently change objective/policy, override hard conditions, or grant exceptions, disclosures or final approval. Bind suggestions/results to current context and reject stale/expired results. A decline ends that invited exception round without repeated pressure. Keep change permission, exact-text/audience disclosure permission and unanimous exact-plan approval independent.
5. Define public answers such as “A proposal is ready under the agreed workload policy” from actual state. Questions like “Who blocked 11?” must not reveal private attribution. Never claim an unaccepted proposal is an agreement. Explain that final outcomes can permit inference; do not promise zero leakage.
6. Document a minimal AWS design using the existing Bedrock, Lambda/API, Cognito, DynamoDB and SQS plan. Verify current official documentation when selecting model/API capabilities. Application authorization remains authoritative; filtering/Guardrails are optional additional protection. Do not assume native Alexa access or introduce paid calls/resources under this design task.
7. Define evaluation fixtures for invented facts, prompt injection, cross-owner/room access, disclosure refusal, expired/audience-changed disclosures, stale revisions, unsupported objectives, model failure and retry. Specify safe template/form fallbacks and synthetic-only diagnostic evidence. Map each requirement to T02 or existing A05/B05/A05.5 coverage without duplicate ownership.
