# E2E01 scenario checklist — current FF11–FF12 flow

Updated 2026-10-16. Record PASS, FAIL or BLOCKED with expected/observed behavior, deployment and evidence for every scenario. Preserve numbers 1–10 so the earlier reports remain interpretable; their recorded outcomes do not qualify this new release. Scenarios 11–16 are new. Inspect current UI before choosing controls.

## Real application journeys

1. **Two separate accounts.** Sign in with both dedicated users in isolated browser contexts. Confirm correct identity/session separation and groups entry. Read current credential availability privately; capture a rejection's safe status/reference rather than guessing its cause.
2. **Group persistence.** Create and rename a clearly owned synthetic group. Refresh/reopen; confirm saved name and correct organizer. Do not reuse/delete the previous run's group without first reading its current ownership/state.
3. **Invitation.** Invite User 2 and accept in their session. Confirm shared membership and separate sessions; keep invitation URLs out of screenshots/reports.
4. **Detailed AI creation.** Describe a fictional dinner with two exact dates and three named venues, with optional estimated prices as context. Review/edit the AI-suggested choices and short title, rename and create. Expect all six date/venue combinations to be representable; no redundant question about which supplied date the group prefers. Each person's preference belongs in their private answers. Do not assert an exact model sentence, real prices or verified availability.
5. **Incomplete idea and helpful questions.** Use a different domain, such as a shared outing, and the example inside the creation modal. Start with incomplete details. Expect an editable draft and a specific missing-choice question, not a repeated unsupported-format dead end. Save/reopen the incomplete draft, enter the missing options, and create. If using optional Ask AI to help with missing details, make an explicit request and confirm existing entered options remain; do not retry unchanged automatically.
6. **Open decision modal.** From the group and a direct decision link, Open decision must open the native dialog itself: short summary/title/status, current user's saved-answer summary, public participant progress and What works for you? choices. No separate shared-choice confirmation screen or three-step private review wizard is required. Opening submits nothing. Check focus, close/Escape, unsaved-work warning, narrow/mobile width and light/dark readability. Finished decisions must not show an editable answer form.
7. **Independent private answers.** User 1 saves synthetic choices before User 2 acts, using explicit processing consent and Save my answers. No waiting for another person's review. User 2 saves different compatible choices independently. Reopen both; each sees their own saved answers and only permitted public progress about the other person. Optional notes are not a mandatory AI step. No selection/private note leaks across sessions.
8. **Proposal and explicit approval.** With compatible answers, Find an outcome starts reasoning; inspect the proposal through See proposal. Each user's final approval remains separate and explicit. Confirm a final shared outcome/status; opening, saving answers or one person's approval never approves for the other. If there is no compatible outcome, use the actual conflict path and record it rather than inventing agreement.
9. **Join while ongoing.** In another group, save User 1's ongoing-decision answers before inviting User 2. Accept/include User 2; existing answers/progress stay, with no repeat review solely for joining. User 2 supplies their own answers. Use only the two existing accounts.
10. **Join after completion.** Complete a User-1-only decision, then add User 2 to that group. Confirm joining does not reopen/change the completed decision, outcome or historical approvals. Respect permitted historical visibility; no third account is needed.
11. **Create without AI.** From Add or edit choices without AI, build a different synthetic decision, for example a shared purchase with three items and two pickup days. Save, reopen/edit and create through the normal authenticated UI, then open its answer modal. This route must not depend on AI request-inventory success or make a provider request. Correlate network/server evidence if available; UI alone does not establish provider-side absence. It can run independently if the AI scenarios fail.
12. **Focused editable validation.** In one owned draft, check a missing label/option, blank/duplicate option and invalid exact date. Expect specific prompts; incomplete drafts can save but cannot create. Correct each issue and create successfully with YYYY-MM-DD dates. No unsupported-format loop, discarded idea or inferred personal preference. Named choices may express dates when an exact date is not known.
13. **Combination limits.** Enter nine named options in one topic and eight in another: 72 combinations. Expect a useful limit prompt and blocked creation, with editable saved content. Reduce to eight by eight: 64 combinations is allowed by validation. Respect six-topic/sixteen-options-per-topic limits and distinguish a capacity/prerequisite failure from a combination-validation failure. No AI call is needed.

## Recovery subcases

Prefer an observed real failure where available. Otherwise use only this agent's own isolated browser response interception/delay, clearly labelled INJECTED in the report. Do not disrupt the public service, mutate cloud controls or call injected evidence a live provider PASS. Run these subcases separately from the real AI success journey above.

14. **Failed AI still permits progress.** Observe or inject a failed/incomplete draft response or unavailable request inventory. The current public idea and any saved draft/answers survive. The editor offers focused repairs and Add or edit choices without AI remains usable; there is no automatic paid retry. The original request key/status is retained, and an unknown request is not falsely declared failed/closed. Manually complete/save/create without overwriting or deleting that original uncertain record.
15. **Reload, interrupted saves and late results.** First save/reopen public idea/options, then refresh the same browser context: current public edits/checkpoints remain, without passwords or private participant answers in this creation cache. Delay/drop only the response to an owned save and inspect recovery: retry/reconcile uses the exact saved request key/body, creates no duplicate and never silently creates an older plan over newer edits. A delayed earlier AI result must not overwrite newer manual edits. Separately fail only the group-list refresh after a known successful save/create; success remains visible/recoverable. Read back state before any retry; unknown backend outcomes stay UNKNOWN. Record browser-only evidence separately if server idempotency cannot be verified.

## Answer-edit follow-up (live)

16. **Change one person's answers.** On an owned active two-user decision with a proposal, User 1 explicitly changes/saves their answers. User 2's saved answers and shared terms remain. The old proposal and dependent approvals/permissions cannot authorize a new outcome; a new proposal needs fresh explicit final approvals. Actual shared-term/version changes keep their stale-save protections. Do not reopen a completed decision to perform this scenario.

## Evidence and independence

Use multiple synthetic domains, not ten retries of one restaurant prompt. Reuse owned fixtures where safe, with exact state/version recorded. Keep provider calls limited to explicit scenario needs. If an account fails, continue its usable peer's independent creation/validation/modal checks; dependent two-user scenarios remain BLOCKED.

For each distinct failure capture UTC, exact visible error/reference, safe HTTP status, correlated permitted log finding or exact denial, and next action. Retain sanitized screenshots for the editor, validation prompts, actual modal/public progress, final outcome and failures; include paths/artifact links in the dated report. Never retain passwords, tokens, invitation URLs or either person's private inputs in shared evidence. Do not erase unknown request records or infer a reliability percentage from this sample.
